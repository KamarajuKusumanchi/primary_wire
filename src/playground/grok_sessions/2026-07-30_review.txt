### Code quality & speed
**Quality**
- Docstrings and comments are extremely detailed—sometimes longer than the code they describe. This is valuable while the edge cases are still being discovered, but many can be shortened once the behavior stabilizes. Prefer “why” over “what the code already shows.”
- Consistent use of `from __future__ import annotations`, dataclasses, Path, and structured logging is good.

**Speed**
- Sequential execution + polite delays (10–30 s) is intentional and correct for courtesy. Parallelism should be introduced carefully (the batched-merge design already anticipates a `ThreadPoolExecutor`).
- Q4 Playwright launches are the main cost. Reuse a single browser context across sources that share the same domain or theme where safe; keep the existing “launch once per scraper” pattern for isolation.
- Cache rendered listing HTML (with a short TTL) for development / smoke tests so you don’t re-render every time.
- For pure-HTTP scrapers (InvestorRoom, most Notified), concurrent requests with a domain-aware semaphore would be a low-risk win once the sequential baseline is solid.
- Avoid detail-page fetches unless `needs_detail_page_dates` or `--fetch-detail-pages` is set; the listing-page heuristics already recover most dates.
