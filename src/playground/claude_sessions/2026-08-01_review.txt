## Overall impression

This is a well-run early-stage project. ## Worth refactoring

**`scrape_notified.py` vs `scrape_notified_gated.py`** is the standout case. `resolve_source`, `is_detail_url`, `build_arg_parser`, `scrape_and_filter`, and `main` are near-duplicates between the two files (I diffed them — same shape, different constants/precedence details). That's a strong signal these two should share one `resolve_source`/`scrape_and_filter` in `scrape_notified_utils.py`, with the gated variant only overriding `get_year_url`/`build_year_url`. Right now a bug fix in one (there's already a comment referencing "the same bug fixed for scrape_investorroom.py and scrape_notified.py") has to be manually ported to the other by hand, and it shows — the two `resolve_source` docstrings are already drifting relative to each other.

## Gaps for scalability/extensibility

1. **No CI.** No `.github/workflows` at all, despite having a real pytest suite with markers and a `--smoke-test` mode built exactly for this. This is the single highest-leverage thing to add — a GitHub Actions job running `pytest` (and maybe `invoke smoke-test` on a schedule) on every PR would catch scraper regressions before they land, which matters a lot given how brittle scraping code inherently is.
2. **No linting/type-checking config.** No `ruff`, `mypy`, or `black` in `pyproject.toml`. The code already uses `from __future__ import annotations` and full type hints consistently, so `mypy --strict` would probably pass with light effort and catch real bugs (e.g. the `Optional` vs default mismatches that tend to creep into argparse-heavy code).
3. **Missing tests for real surface area**: `scrape_investis.py` (762 lines) has no test file at all. Neither does `csv_utils.py` or `scrape_notified_utils.py`, despite being the most shared/load-bearing modules. `update_source.py`/`update_release.py` (the interactive scripts contributors actually run) are also untested.
4. **55 "unknown platform" sources** per `scraper_coverage_summary.txt` — no automated scraper category exists for them yet. As coverage grows past S&P 500 (which the README says is in scope), you'll keep hitting new platforms; the "one scraper module per platform + shared utils" pattern scales fine, but `detect_ir_platform.py` classifying more platforms automatically (rather than a human eyeballing each new IR site) is the real leverage point for getting past 15.8%.
5. **Data layout**: one CSV per calendar day is simple and diff-friendly now (147 files, 600K), but at S&P 500 + government-agency scale over years this will be thousands of small files in one flat `data/YYYY/` directory. Worth deciding now whether that's fine forever (git handles it) or whether monthly/quarterly files reduce file-count sprawl before it's painful to migrate.
